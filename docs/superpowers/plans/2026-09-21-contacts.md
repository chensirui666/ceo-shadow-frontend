# Contacts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a local-demo Contacts workspace where a user explicitly reviews candidates before creating, inspecting, filtering, editing, refreshing, inviting, or deleting people profiles.

**Architecture:** Keep all Contacts business rules in a small immutable state module and a session-scoped fixture service, following `libraryState.ts` and `libraryService.ts`. `ContactsWorkspace.tsx` owns only UI state and calls that service; `Workspace.tsx` owns the one service instance and adds the route.

**Tech Stack:** React 19, TypeScript, HeroUI, lucide-react, CSS, Node's built-in test runner, Vite SSR component tests.

**Spec:** `docs/superpowers/specs/2026-09-21-contacts-prd.md`

## Global Constraints

- This repository is a local front-end demo: do not claim real Connector reads, Agent execution, identity matching, persistence, or external Team invitations.
- Candidates represent only the PRD's permitted evidence; confirming is the sole path that adds them to the Contact list.
- The product shows one pre-merged fixture identity across sources but implements no cross-Connector identity matching.
- Preserve the required English Contacts explanatory sentence exactly under the list title.
- No dependency additions; reuse the installed HeroUI, lucide-react, connector logos, and existing workspace styling conventions.
- Do not expose message bodies, email bodies, prompts, reasoning, or internal logs in the UI.

## Review Focus

- A query must match the visible name, relationship description, or source identity name and combine with both time and source filters.
- A candidate must never appear in the list before `confirmCandidates` is invoked, including after an empty discovery result.
- Removing the final source must preserve the profile and historical text while ensuring that source is absent from future refresh input.
- Editing must preserve untouched source identities and the optional user-written context separately from observed profile facts.
- A profile refresh and Team invitation must mutate only the selected contact; neither may create another contact or use an external Connector.

- [ ] **Step 3: Implement the minimal immutable state boundary and fixture service**

```ts
export type ContactProfile = {
  summary: string
  recentContacts: string
  relationship: string
  context: string
}

export type Contact = {
  id: string
  name: string
  relationship: string
  sources: Array<{ connector: ConnectorId; name: string }>
  lastInteractionAt: string
  profile: ContactProfile
  contextPrompt: string
  refreshedAt?: string
  invitedAt?: string
}

export const selectContacts = (contacts: Contact[], filters: ContactFilters, now: Date): Contact[] => contacts
  .filter((contact) => matchesContact(contact, filters, now))
  .sort((a, b) => Date.parse(b.lastInteractionAt) - Date.parse(a.lastInteractionAt))

export const confirmCandidates = (contacts: Contact[], candidates: ContactCandidate[], ids: string[]): Contact[] => [
  ...contacts,
  ...candidates.filter((candidate) => ids.includes(candidate.id) && !contacts.some((contact) => contact.id === candidate.id)),
]

export const createContactsService = (initial: Contact[] = []) => {
  let contacts = structuredClone(initial)
  const candidates = createContactCandidates()
  let preview: ContactCandidate[] = []
  return {
    load: async () => structuredClone(contacts),
    discover: async (connected) => { preview = candidates.map((candidate) => ({ ...candidate, sources: candidate.sources.filter((source) => connected.includes(source.connector)) })); return structuredClone(preview) },
    confirm: async (ids: string[]) => { contacts = confirmCandidates(contacts, preview, ids); return structuredClone(contacts) },
  }
}
```

Include source-name edits, optional `contextPrompt`, source removal, profile-only refresh timestamp, and an `invitedAt` local status. Fixture candidates must be pre-qualified and use only `dingtalk`, `feishu`, and `teams` identities.
