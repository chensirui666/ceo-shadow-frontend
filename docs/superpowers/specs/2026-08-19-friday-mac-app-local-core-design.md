# Friday Mac App 本机后端设计

## 目标

Friday 首期交付为一个 Mac App，而不是业务 Web。用户安装一个应用；它在窗口关闭后驻留菜单栏，并在用户登录 macOS 后自动恢复运行。它读取用户授权的钉钉信息，在本机生成并保存回复，首期绝不向钉钉外发。

云端只提供成熟的邮箱验证码登录与“账号当前在哪台 Mac 工作”的最小登记。云端不保存、处理或转发钉钉内容、Message、Memory、草稿、模型输入输出或模型 API Key。

## 已确认边界

- 产品是 Desktop-first 的 Friday Mac App；首期没有业务 Web。
- 一个 Friday 账号同一时刻只有一台活跃 Mac，并只绑定一个钉钉工作身份。
- 同一账号可以在另一台 Mac 登录；新 Mac 创建空白本地工作空间，不自动同步旧 Mac 数据。用户明确确认“在这台 Mac 开始工作”后，旧 Mac 停止后台处理；旧数据保留在旧 Mac。跨 Mac 数据迁移是后续独立能力。
- 用户通过自己的钉钉账号授权；首期只读取群聊中明确 @ 当前用户的新消息。
- 用户提供自己的 DeepSeek API Key。Friday 固定一个 DeepSeek 模型，不开放模型选择；Key 只保存到 macOS 钥匙串，Rust 直接调用 DeepSeek。
- 首期只有 Message：生成、保存和查看回复；不创建 Task、不收集 Feedback、不调用或伪造 Memory、不向钉钉外发。
- Memory 是未来的本机模块，可与 Message 并行开发，但不是 Message MVP 的运行依赖。前端不得直接请求尚不存在的 Memory 服务。

## 运行形态

用户视角中只有一个 Friday App：

- 点击窗口红叉：隐藏窗口，Friday 留在菜单栏继续运行。
- 点击“暂停工作”：停止接收与生成新的 Message，保留既有记录。
- 点击“退出 Friday”或使用 `Command-Q`：App 与后台工作同时停止。
- 用户登录 macOS 后：Friday 自动启动，在菜单栏显示状态。

实现上，React/Vite 是界面，Tauri/Rust 是本机后端。二者通过 Tauri 内部调用通信；不启动本机 HTTP 服务，不引入 API 网关。

```text
Friday Mac App
├─ React / Vite 界面
└─ Tauri / Rust 本机后端
   ├─ 账号与本地工作空间
   ├─ 权限与发送门禁
   ├─ 钉钉 DWS 连接
   ├─ SQLite 本地记录
   ├─ Message 处理逻辑
   ├─ Memory 处理逻辑（后续）
   ├─ DeepSeek 调用
   └─ 后台任务调度
```

这些是同一个本机后端中的并列职责，不是独立微服务。后台任务调度只负责何时执行、有限重试和重启恢复；它不高于或替代 Message、Memory、DWS 或 SQLite 的业务职责。

## 各职责

| 职责 | 只负责什么 | 不负责什么 |
| --- | --- | --- |
| 账号 | 将登录用户映射到正确的本地工作空间 | 钉钉读取或业务判断 |
| 权限 | 判断消息是否符合处理范围 | 调用钉钉或模型 |
| 钉钉 DWS | 登录钉钉、监听事件、读取获批准的上下文 | 判断是否应回复 |
| SQLite | 保存事实、状态与去重记录 | 调用钉钉或模型 |
| Message 处理逻辑 | 根据当前 Message 生成用户可读结果 | 直接外发消息 |
| Memory 处理逻辑 | 后续从用户授权的资料提炼长期记忆 | 阻塞首期 Message |
| DeepSeek 调用 | 用最小必要上下文完成模型推理 | 保存用户业务资料 |
| 发送门禁 | 对外发前的最后硬性判断 | 生成回复内容 |
| 后台任务调度 | 执行、恢复和有限重试耗时工作 | 改写业务决策 |

## 身份、设备与本地隔离

成熟的邮箱验证码服务提供稳定的 Friday 用户 ID。Friday 只额外保存用户 ID 与当前活跃 Mac 的设备登记。

每个 Friday 用户在本机拥有独立工作空间，包含独立的 SQLite 数据库、钉钉连接状态、Message、后续 Memory 和相关本地文件。退出账号时，Friday 停止这个账号的后台处理并锁定工作空间，不删除资料；重新登录同一账号后可恢复。

登录凭证和 DeepSeek API Key 存在 macOS 钥匙串，不进入 SQLite，也不进入云端。SQLite 用于可靠持久化，不等同于加密；本机磁盘保护依赖 macOS 用户隔离与 FileVault。

## 钉钉接入

用户在 Friday 中点击“连接钉钉”后，Rust 后端执行以下流程：

1. 检查 DWS 是否可用；
2. 未安装时，向用户说明将安装 DWS，获得确认后执行其官方安装方式；不在 Friday 包内默认安装，也不静默安装；
3. 启动 DWS 的钉钉登录／授权流程；Friday 不保存 DWS 凭证副本；
4. 若 DWS 有多个组织或账号，用户明确选择一个钉钉工作身份；
5. 该身份绑定到当前 Friday 工作空间；
6. Friday 启动 DWS 的个人 IM 长连接监听。

首期使用事件驱动监听，不轮询消息历史。监听到事件后，Friday 只接受群聊中明确 @ 当前用户的新消息。未 @ 用户、历史消息、私聊、会议、审批、文档 @ 和其他来源都不创建真实 Message。

## Message 数据流

```text
DWS 监听到钉钉事件
→ 权限检查：是否是当前已绑定身份的明确 @消息
→ SQLite：按稳定钉钉消息 ID 创建一条 Message
→ Message 处理逻辑读取本次必要上下文
→ DeepSeek：直接生成处理结果
→ SQLite：写入用户可读的判断依据、回复和终态
→ React：展示同一条 Message
```

React 不直接调用 DWS、SQLite、DeepSeek 或任何后端模块。所有界面操作都经 Tauri 调用本机后端。

每条 Message 保存：来源身份、发送人、会话、原文、接收时间、稳定消息 ID、用户可见状态、用户可读判断依据、生成回复、失败原因、重试结果及必要更新时间。首期不保存模型内部推理。

Message 使用当前 `03-Message PRD.md` 的用户状态：

```text
待处理 → 处理中 → 已处理（已生成回复，未外发）
                  ├→ 已跳过
                  └→ 处理失败
```

`待确认`保留为未来真实外发能力的领域状态，但首期不在界面暴露确认外发操作。Message 有生成结果后叫“回复”，不在产品界面称为“草稿”。

## Memory 的并行边界

Memory 会作为 Friday 本机后端中的单独处理逻辑开发：它接收用户授权资料，提炼并保存长期工作记忆。它不是云端服务，也不应被 React 直接调用。

在 Memory 模块尚未可用时：

- Message 只使用当前消息与本次允许读取的最小上下文；
- Message 的处理依据不展示伪造的 Memory 引用；
- Onboarding 或 Memory 页面不得把未执行的后台任务显示为成功；
- 前端可并行完成界面，但正式集成仅在本机模块可用后发生。

## 安全与可靠性

- 首期发送门禁无条件拒绝所有钉钉外发；即使界面或模型输出要求发送，也不得绕过。
- SQLite 对钉钉消息 ID 施加唯一约束。DWS 重连、应用重启和自动重试不得创建重复 Message。
- DWS 与 DeepSeek 的短暂失败执行有限自动重试；仍失败后将同一 Message 标为“处理失败”，允许用户手动重试。
- DWS 断开是连接状态，在 Settings 和菜单栏提示；不伪装成一条 Message 的状态。
- 模型输入只包含本次生成必要的内容。它不会经过 Friday 云端，但会发送给 DeepSeek；产品必须如实说明这一点。
- 首期没有任何钉钉写操作。未来外发必须新增独立的确认流程、最小权限和持久化审计，不能只改前端状态。

## 验证

自动化测试至少覆盖：

1. Friday 账号之间的本地工作空间隔离；
2. 新 Mac 空白登录与明确切换活跃 Mac 的行为；
3. 钉钉消息 ID 去重；
4. `待处理 → 处理中 → 已处理／已跳过／处理失败` 的合法状态流转；
5. DWS 事件解析与“群聊明确 @ 当前用户”过滤；
6. DeepSeek 响应的结构和失败处理；
7. 首期发送门禁永远拒绝外发。

首条端到端验收链路：

```text
新 Mac 登录
→ 用户确认安装并登录 DWS
→ 选择一个钉钉工作身份
→ 收到一条明确 @用户 的群消息
→ Friday 只创建一条 Message
→ DeepSeek 生成回复
→ Message 显示“已处理，未外发”
→ 钉钉没有任何 Friday 外发消息
```

## 明确不做

- 业务 Web、远程控制台、云端业务数据库或跨设备自动同步；
- 打包、静默安装或重新实现 DWS；
- 多钉钉身份、多活跃 Mac、私聊、未 @ 群消息、会议、审批、文档消息；
- Memory、工作风格、Task、Feedback、真实外发或外部反馈；
- 任意模型选择、自定义模型地址、云端代理模型请求；
- 本机 HTTP API、独立微服务、消息历史轮询、模型思维链或技术日志展示。

## 后续顺序

1. 以同一套本机边界接入真实 Memory 与工作风格任务；
2. 增加 Task 和 Feedback，但不改变 Message 的事实来源与状态；
3. 增加确认后的真实外发及其单独门禁和审计；
4. 提供显式的本地数据迁移；
5. 只有在确有远程访问需求时，重新评估业务 Web 和端到端加密转发。
