# Friday Message NPS 方案

| 字段 | 内容 |
| --- | --- |
| 日期 | 2026-08-20 |
| 状态 | 已确认，待实施规划 |
| 所属页面 | Message 详情 |

## 1. 目标

用一次标准 NPS 评分判断用户是否认为 Friday 整体值得推荐，而不是评价某一条回复写得好不好。

首期只收集 0–10 分，不要求说明原因、不创建待办、不改变工作画像，也不和现有的 Message 点赞／点踩或 Feedback 质量驾驶舱混合。

## 2. 触发与展示

用户必须同时满足以下两个条件，才具备一次评分资格：

1. 自首次正式启用 Active 起已满 7 天；
2. Friday 已完成至少 3 条真实协助回复，且每条回复成果物均已确认外发。

- Trial 草稿、待确认但未发送、处理失败、已跳过、本人手动处理，以及文档／审批等非回复成果物，都不触发。
- 后端在两个条件都满足时写入评分资格；用户之后打开任一已处理 Message 的详情时，才展示一次评分卡。因此不使用弹窗，也不打断外部工作。
- 评分卡位于详情的“回答／处理结果”之后，文案为：`你有多大可能把 Friday 推荐给同事或朋友？`
- 卡片提供 0–10 十一个可点击数字；辅助标记为 `0 完全不会` 与 `10 非常可能`。
- 点击一个数字即保存。保存成功后显示“感谢你的评分”，不再显示选项。
- 首期每位用户只能提交一次 NPS；不提供修改、稍后提醒、追问原因或再次邀请。

## 3. 数据边界

NPS 是独立的产品体验数据，不能写入 Message 的回复反馈记录或 Feedback 页面。

服务端保存一条评分至少需要：用户标识、评分（0–10）、首次正式启用时间、满足资格的第三条 Message ID 和回复成果物 ID、具备资格时间、提交时间。服务端以用户标识施加唯一约束，避免多个浏览器或重复点击产生多条评分。

前端只读取“该用户在当前 Message 是否应显示 NPS”和提交评分；不自行从 Message 状态推断真实外发，也不计算或伪造评分结果。

## 4. 指标与判定

| 分数 | 分类 |
| --- | --- |
| 9–10 | 推荐者 |
| 7–8 | 中立者 |
| 0–6 | 贬损者 |

`NPS = 推荐者占有效评分的比例 − 贬损者占有效评分的比例`，取值范围为 -100 到 +100；中立者计入分母但不加不减。

同时记录：具备资格用户数、评分卡实际展示数、有效评分数和回收率。汇总指标仅作为内部产品度量，不放入 Message 或 Feedback 的用户页面。

当有效评分少于 30 个时，只观察分数和回收率趋势；达到 30 个后，NPS 大于 0 才可作为“推荐者多于贬损者、产品价值获得初步验证”的信号。它不等同于长期留存、付费意愿或单条回复质量。

## 5. 异常与真实边界

- 提交失败时，保留评分选项并显示“评分未保存，请重试”；服务端去重保证重试安全。
- 已提交的评分再次进入详情时只显示感谢状态，不重复提交。
- 当前前端仍是本地演示、没有经验证的真实外发链路，因此不得默认展示 NPS 卡片、生成模拟评分，或宣称 NPS 已采集。只有显式的本地演示场景才可展示，并必须标注“本地演示”。

## 6. 验收

1. 只有首次正式启用满 7 天、且已有至少 3 条真实协助回复外发确认成功的用户会具备资格；任一单条回复均不会单独触发。
2. 具备资格后，评分卡只在用户随后打开的已处理 Message 详情“回答／处理结果”之后出现一次。
3. 0–10 任一点击能保存一次评分；重复点击、重复进入和多端请求不会产生第二条记录。
4. 失败重试不丢失用户选择，也不会造成重复评分。
5. 评分分类、NPS 计算、有效评分数与回收率符合第 4 节定义。
6. Message 点赞／点踩、Feedback 卡片和工作画像不读取、展示或修改 NPS 评分。
