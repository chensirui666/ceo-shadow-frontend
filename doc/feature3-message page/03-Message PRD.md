# Friday 03｜Message PRD

| 字段 | 内容 |
| --- | --- |
| 文档版本 | v1.1 |
| 创建日期 | 2026-08-13 |
| 所属阶段 | 信息驱动工作流的入口页：让用户看见外部信息、Friday 的判断与处理结果 |

## 1. 一句话定义

**Message 是 Friday 接收到的一条外部工作信息，以及 Friday 对这条信息的判断、处理和结果。**

Message 页不是钉钉／飞书的聊天替代品，也不是运行仪表盘。用户打开它，只需要快速知道：谁提出了什么、Friday 为什么这样判断、它已经如何处理。

## 2. 背景与目标

### 2.1 背景

用户的工作请求散落在群聊、会议、审批和文档中。现有 Home 的事件流以“系统做了什么”为组织方式，用户仍要自行判断哪些事件对应一件真实工作、Friday 的回答是否恰当。

Friday 的价值不在于把所有渠道搬进新应用，而在于把与本人有关的外部工作信息变成可读、可审计的处理结果。Message 因此是信息驱动工作流的唯一入口；Task、Memory 和 Feedback 都与某条 Message 关联，但不改变它作为原始工作案卷的角色。

### 2.2 用户目标

用户进入 Message 后，应能：

1. 按时间看到所有符合规则的外部工作信息；
2. 第一眼同时看见对方的问题和 Friday 的处理；
3. 对需要授权的结果直接确认或跳过；
4. 对一次 AI 输出点赞或给出负反馈；
5. 在详情中理解 Friday 的判断依据和完整结果；
6. 看见这条信息是否自动产生了 Task，而不把 Task 当作 Message 的状态。

### 2.3 成功标准

- 每条 Message 在列表中都可读出来源、对象、状态、外部问题和 Friday 的处理。
- 用户无需进入详情，即能完成待确认 Message 的确认或跳过。
- 详情能按“问题 → 判断依据 → 回答／处理结果”说明 Friday 的决定；不暴露模型原始思维链或技术日志。
- Message 创建 Task 后仍可成为`已处理`，不会因为后续工作未完成而被错误标为处理中。
- 未接入真实连接器或发送门禁时，页面明确处于本地演示边界，不伪造外部处理结果。

## 3. Message 定义与进入规则

### 3.1 定义与边界

Message 只指外部进入 Friday 的原始工作信息。它保存原始触发、来源、状态、处理结论、成果物、关联 Task 和审计引用。

Message 不复制整段聊天、整场会议或整份文档；长期背景和材料归入 Memory。Message 只记录本次处理引用了哪些 Memory／材料，供审计时查看。

### 3.2 创建条件

| 类别 | 创建 Message 的条件 |
| --- | --- |
| 聊天 | 有人明确 @ 本人。 |
| 会议 | 本人参会，会议结束且会议内容已可用。 |
| 审批 | 当前轮到本人审批。 |
| 文档 | 有人在文档中明确 @ 本人。 |

不满足条件的群聊、尚未结束的会议、未轮到本人的审批和未 @ 本人的文档，均不创建 Message。Friday 为理解一次请求可读取最小必要上下文和相关 Memory，但不会把它们完整存入这条 Message。

### 3.3 用户可见状态

| 状态 | 用户含义 |
| --- | --- |
| 待处理 | Friday 已收到这条信息，尚未开始处理。 |
| 处理中 | Friday 正在理解请求并尝试完成处理。 |
| 待确认 | Friday 已准备好处理结果，但还差一次本人授权。 |
| 已处理 | Friday 已完成这条信息的处理并记录或交付结果。 |
| 已跳过 | 无需处理，或本人选择不让 Friday 继续处理。 |
| 处理失败 | Friday 无法完成原本可处理的动作，且自动恢复未成功。 |

创建 Task 不是 Message 状态。若会议里产生一项后续工作，Friday 可以先在原渠道完成本次回复或同步，再创建 Task；原 Message 仍可为`已处理`。

## 4. 页面设计

### 4.1 视觉布局北极星（桌面端）

本节只约束信息层级、空间关系和阅读顺序，不规定颜色、字号、阴影或图标风格。Message 是桌面工作区中的主页面，不做移动端堆叠方案。

#### 列表页布局

页面采用**左侧应用导航 + 中央 Message 信息流 + 右侧辅助栏**的三段式布局：

1. **左侧应用导航**：固定在窗口左侧，包含 Friday 品牌、一级导航和底部设置／账号入口；当前一级页面为`Message`，Task 与其他工作区入口保留在同一导航层级。
2. **中央主区域**：位于圆角工作画布中，是页面视觉和操作重心。顶部依次为页面标题、状态 Tab、五列字段标题和按时间倒序的 Message 卡片流；列表宽度优先保证“用户问题”和“Friday 的处理”可并排扫读。
3. **右侧辅助栏**：与列表顶部对齐，采用纵向小卡片堆叠，不抢占主信息流。依次放置：常规筛选、来源概览、处理统计和前往设置的能力提示。它们只帮助定位或理解数据，不替代 Message 列表，不展示图表。
4. **全局工具位**：画布顶部右侧保留搜索、通知和账号等入口；未接入的能力必须明确不可用或标注演示边界，不能伪造真实搜索、提醒或渠道连接结果。

右侧栏各块内容如下：

| 区块 | 内容 | 交互边界 |
| --- | --- | --- |
| 常规筛选 | 来源、类别、会话、发起人四个下拉选择器，以及“清除全部”。 | 与顶部状态 Tab 取交集；选项只来自当前已有 Message 和已定义的来源，清除时回到“全部”状态与默认筛选。 |
| 来源概览 | 固定展示钉钉、飞书、Teams、Slack、企微、Discord 六个来源的应用图标、名称和 Message 数量；没有 Message 时显示 0。 | 仅用于概览和筛选，不以数量或图标暗示该来源已经连接成功。 |
| 处理统计 | 全部 Message、待确认、已处理、处理失败四个简短数字摘要，标题旁标明统计范围为“全部消息”。 | 只展示可由当前数据计算的数字；不虚构“最近 7 天”等时间范围，不做趋势图或效果承诺。 |
| 能力提示 | “让 Friday 更聪明”说明和前往设置按钮。 | 按钮打开现有设置工作区；不在空态中替代 Message 内容，不伪造连接成功。 |

#### 详情页布局

详情页沿用相同的左侧导航和工作画布，采用**主阅读列 + 右侧操作栏**：

1. 顶部先显示`Message / Detail`路径、Message 标题与当前状态；下一行横向展示对象、来源、类别、接收时间和团队等已知元信息，未知字段不占位。
2. 左侧主阅读列按“问题 → 判断依据 → 回答／处理结果 → 关联 Task → 反馈 → 处理依据”垂直排列为独立阅读区块。成果物以紧凑预览／下载入口显示；没有成果物时不保留空白容器。
3. 右侧操作栏从上到下固定放置：本条可执行操作（例如确认／跳过）、Message 信息摘要、关联 Task 汇总和处理时间线。时间线只呈现本条 Message 的关键节点，如接收、草稿完成、等待确认、完成／跳过／失败。
4. 详情页的判断依据保持默认展开；处理依据（Memory 和材料引用）保持默认折叠。右侧栏不复制主阅读列的完整正文。

### 4.2 默认视图与筛选

- 页面标题为`Message`。
- 默认展示全部 Message，按创建／接收时间倒序排列。
- 顶部提供状态筛选：`全部 / 待处理 / 处理中 / 待确认 / 已处理 / 已跳过 / 处理失败`。筛选采用横向文字 Tab，所有选项共用一条底线；当前项以底部短线标示，不使用胶囊按钮或独立筛选框。
- 状态只用于筛选，不改变默认排序，也不将页面拆成待办、仪表盘或不同渠道的子页。

### 4.3 信息流卡片

Message 列表采用完整信息流：每条 Message 是统一行高的卡片，而非表格行或常驻双栏详情。

卡片按固定五列从左至右排布，避免用户每次都重新寻找信息：**状态与时间 → 对象、来源、类别 → 用户问题 → Friday 的处理 → 操作**。不使用仪表盘图表、看板列或聊天气泡。

| 区域 | 必须内容与规则 |
| --- | --- |
| 状态与时间 | 显示状态信号、状态文字和接收／创建时间；时间前有时钟图标，采用“月 日，时:分”格式，不显示年份。 |
| 对象、来源、类别 | 以发起人头像（无头像时用稳定占位）和姓名说明是谁给本人发起了这条工作；来源以应用图标和名称显示，类别为紧凑标签。群／会话、会议、审批或文档名称保留为本条 Message 的上下文，不抢占发起人信息层级。 |
| 用户问题 | 对方的问题、会议结论、审批请求或文档请求。默认最多 2–3 行。 |
| Friday 的处理 | 已发出的回复、已完成结果、待确认原因、跳过原因、处理中说明或失败原因。默认最多 2–3 行。 |
| 操作 | 只放本条可执行操作与反馈，按状态动态出现；确认使用主按钮配对勾图标，跳过使用次按钮配跳过图标，反馈使用点赞／点踩图标。 |
| 全文阅读 | 超出部分折叠；鼠标悬停或键盘聚焦时可查看完整内容。点击卡片进入详情。 |
| Task 关联 | 有 Task 时只显示`已创建 N 个 Task（N 个待完成）`入口，不在 Message 流展开 Task 标题。 |

### 4.4 行内操作

| 条件 | 操作 | 结果 |
| --- | --- | --- |
| 待确认 | `确认`、`跳过` | 更新同一条 Message；确认后处理为`已处理`，跳过后为`已跳过`。 |
| 有 Friday 输出 | `点赞`、`点踩` | 点赞直接记录；点踩后在当前卡片上方展开原因输入栏。 |
| 处理失败 | `重试` | 重新请求 Friday 处理。失败出现前应先由 Friday 自动重试。 |

点踩原因提交后仅进入 Feedback，绑定这次外部输入和 Friday 输出。它不自动改写已发结果，不自动修改 Memory，也不在本期定义何时改变未来行为。

### 4.5 详情页

详情按固定的工作阅读顺序呈现：

1. **问题**：完整原始外部信息和来源元信息；
2. **判断依据**：Friday 理解到的请求、关键事实，以及为什么选择直接处理、待确认、跳过或创建 Task；默认展开；
3. **回答／处理结果**：完整回复、文档、审批意见或其他已完成结果，以及是否已外发；
4. **关联 Task**：只读列出由该 Message 创建的 Task 和当前状态；
5. **反馈**：点赞／点踩和已提交的负反馈原因；
6. **处理依据**：默认折叠，按需查看本次使用的 Memory 和材料引用。

“判断依据”是面向用户的决策说明，不展示模型内部推理过程、原始 Prompt、工具调用、数据库标识符或无关上下文。

### 4.6 空态与异常态

- 无数据时仅提示：`Friday 正在等待 @你、会议结束、轮到你审批或文档 @你。`
- 不放模拟 Message、连接器推荐或新建 Message 按钮。
- 失败 Message 先自动重试；仍不能恢复时显示可读原因和`重试`。只有需要本人采取行动的不可恢复失败才单独通知本人。

## 5. 与 Task、Memory、Feedback 的关系

| 对象 | Message 接收什么 | Message 不做什么 |
| --- | --- | --- |
| Task | 自动创建的 Task 数量与状态入口。 | 不把 Task 标题、进度或外部执行过程塞进信息流；不把 Task 未完成当作 Message 状态。 |
| Memory | 本次判断引用的资料和工作背景。 | 不复制长期 Memory 或整段上下文。 |
| Feedback | 对本次 Friday 输出的点赞或点踩原因。 | 不承诺自动训练、自动改写已发结果或自动修改 Memory。 |

## 6. 关键用户流程

### 6.1 Friday 可直接处理

1. 符合进入规则的外部信息创建 Message；
2. Friday 判断并在授权范围内完成回复／结果；
3. Message 显示`已处理`和结果；
4. 用户可查看依据并反馈，不会收到不必要的单独提醒。

### 6.2 需要本人确认

1. Friday 准备好结果，但识别到需要本人授权；
2. Message 显示`待确认`，卡片可直接确认或跳过；
3. 本人确认后，Friday 完成原渠道动作，Message 变为`已处理`；
4. 本人跳过后，Message 变为`已跳过`。

### 6.3 产生后续 Task

1. Friday 从 Message 中识别出需要本人在外部工具完成的工作；
2. Friday 完成本次可完成的回复或同步，Message 可变为`已处理`；
3. Friday 自动创建关联 Task；
4. Message 卡片只显示 Task 计数，用户在 Task 页查看完整上下文并自行处理。

## 7. 数据与实现边界

页面应通过可替换的数据服务消费稳定的 Message 领域数据，至少需要：来源应用、类别、对象、原始请求、状态、接收时间、Friday 处理说明、完整结果、Task 汇总、反馈、失败原因和审计引用。

当前前端 Home 使用本地 fixture／浏览器会话数据；后续接入真实服务时，只替换数据服务，不让 UI 直接耦合钉钉、飞书、会议、审批或文档 API。真实外发、确认与重试必须受后端权限和发送门禁控制，不能由前端状态伪造。

## 8. 非目标

- 不做聊天、会议、审批或文档的原渠道跳转；
- 不允许手动新建 Message；
- 不显示完整群聊、完整会议转写、原始日志或技术审计后台；
- 不把 Message 做成按渠道拆分的工作台；
- 不在本期提供用户可编辑的授权 Prompt 或自动学习阈值配置。

## 9. 指标、依赖与风险

### 9.1 首期观察指标

首期只记录真实可验证的页面行为，不伪造“节省时间”等效果指标：

| 指标 | 定义 |
| --- | --- |
| Message 覆盖 | 符合四类进入规则的外部事件中，成功形成可读 Message 的比例。 |
| 待确认处理率 | 进入`待确认`的 Message 中，被确认或跳过的比例及处理时长。 |
| 处理可解释性 | 有输出的 Message 中，具备用户问题、判断依据和处理结果的比例。 |
| 反馈留存 | 点踩时成功关联原始输入、Friday 输出和用户原因的比例。 |

### 9.2 依赖与风险

| 项目 | 依赖／风险 | 产品处理 |
| --- | --- | --- |
| Message 进入 | 聊天 @、会议内容、审批轮次和文档 @ 需要稳定的渠道数据。 | 未接入前明确为本地演示；不伪造实时外部信息。 |
| 外发与确认 | 前端不能代替真实发送和权限门禁。 | 真实动作必须由后端受控执行并回写审计结果。 |
| 判断依据 | 解释不足会让用户不信任，解释过多会暴露技术过程。 | 固定输出用户可读的关键事实和决策原因，材料引用按需展开。 |
| 负反馈 | 反馈收集不等于自动学习。 | 只进入 Feedback；任何改变未来行为的机制另立需求。 |

## 10. 验收标准

1. 只有符合四类进入规则的外部事件可创建 Message。
2. 默认列表按最新时间展示全部 Message；状态筛选完整可用。
3. 卡片统一高度，完整显示元信息、截断后的用户问题和 Friday 处理；悬停／聚焦可读全文。
4. 待确认可在卡片直接确认或跳过，且只更新同一条 Message。
5. 点踩在当前卡片展开原因输入；提交后可在 Feedback 追溯，既不自动改已发结果，也不自动改 Memory。
6. Message 创建 Task 后仍保持自己的处理状态，不出现`跟进中`这一 Message 状态。
7. 详情严格按“问题 → 判断依据 → 回答／处理结果”解释处理，并能查看关联 Task 和折叠的材料引用。
8. 无数据、自动重试、失败重试和本地演示边界均有用户可读状态。
