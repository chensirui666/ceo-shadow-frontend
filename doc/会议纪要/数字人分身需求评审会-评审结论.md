# 数字人分身需求评审会｜评审结论

> 会议时间：2026-08-14
>
> 原始记录：[数字人分身需求评审会](./数字人分身需求评审会.md)

## 一句话结论

一期收敛为“单一连接器上的聊天处理 + Memory”。先做出可靠的闭环，再扩展会议、审批、任务、团队概览和多渠道能力。

## 一、已达成一致，可直接修改 PRD 与排期

1. Onboarding 从四步改为三步：连接工作入口 → 构建 Memory → 生成并确认工作风格。删除“先试一次”的独立步骤，但保留用户修改工作风格的入口。
2. Onboarding 不应只是一次性新手引导，应定位为可重复执行的初始化工作流；更换连接器时重新执行连接、资料读取和风格生成。
3. 一期一个用户只绑定一个连接器，不做钉钉、飞书、Teams 等多源混合检索。
4. 一期 Message 只支持聊天触发；会议、审批、文档触发延后。Memory 是一期核心能力。
5. Task 页面不进入一期，避免产生大量低价值待办。
6. 反馈、消息统计和运行观测统一放进 Data Board，避免多个页面重复展示看板内容。
7. 应用作为独立产品交付；一期账号体系分开，统一 SSO 后续再做。
8. Settings 一期保留工作节奏、免打扰、@ 规则和“需要我接管”；“连接需处理”“回复发送失败”等通知先不做。

## 二、需要产品与技术共同定案的问题

### 1. Memory 初始化、进度与取消

建议把导入做成后台任务：`拉取资料 → 建索引 → 生成工作风格 → 完成 / 失败 / 已取消`。

- 前台展示处理阶段与粗略预计时间，不伪造精确百分比。
- 用户可离开页面；近期样本达到最低量后即可生成工作风格，全量 Memory 继续后台补齐。
- 取消任务时停止读取，并清理未入库的临时数据。

### 2. 来源隔离与可追溯

即使一期只接一个渠道，导入时也必须保留来源元数据：连接器、原始对象 ID、资料类型、授权范围和导入时间。不要把“来自钉钉”写进正文代替结构化字段。

这样后续才能正确实现多渠道隔离，以及 Message 详情中的“处理依据与材料”。

### 3. 海外连接器优先级

会议中既有“海外客户优先 Teams”，也有“Teams、Slack、Discord 选最快跑通者”的意见，尚未最终定案。

先完成一页 POC 表，再做决定：真实授权、可读取内容、事件触发、能否发送、限流、测试租户、完成闭环所需工期。若 Teams 能按期跑通“读消息—生成—受控发送”，则优先 Teams；否则选择能最快闭环的渠道。

### 4. 自动回复与人工确认

“五分钟未读”只能是等待时间，不能等同于用户授权。

- 低风险且已有明确规则的消息可自动处理。
- 承诺、审批、金额、敏感信息和资料不足的情况一律进入“待确认”。
- 确认、跳过和发送都更新同一条 Message，不能额外制造 Message 或形成自触发循环。

### 5. 处理依据的展示

不展示模型原始推理。页面只展示可审计的处理依据：命中的来源、采用的规则、缺失的信息和需要人工确认的原因。

### 6. 数据存储、迁移与多端支持

先定数据分层：原始聊天资料默认留本机加密；账号侧保存经授权的设置、工作风格和必要任务状态。二期再做用户主动发起的加密导出/导入。

同时明确首发兼容矩阵。Windows 11 是明确优先项；Windows 10 与 macOS 未完成测试前不能宣称已支持。

## 三、产品需要继续调研和设计的问题

1. **Task 的准入规则**：只在 AI 无法闭环、必须由本人判断、线下执行或补材料时创建；只给本人，需去重、上限和汇总规则。
2. **各渠道的高价值事件**：按目标客户和渠道输出表格，定义每个平台 Top 3 工作事件、可访问字段、权限和允许分身处理的范围，不能照搬“聊天、审批、会议”三件套。
3. **二期团队概览与向上汇报**：先定义服务对象、数据授权、汇报频率和可见范围，不能默认汇总团队个人工作数据。
4. **名称与品牌**：独立产品方向已定，但产品名称、商标可注册性、官网表述和安全承诺需要产品与品牌确认。

## 四、协作与非产品待办

- 产品经理完整自审 AI 生成的 PRD，补齐页面、状态、异常、授权、二维码/跳转等交互图。
- 将所有争议点整理成清单，先同架构与技术逐条对齐；必要时再约专项评审会。
- 重新拆分一期、二期和功能清单，按两周实际产能排期；完成产品移交、UI 细节和验收口径后再进入正式开发。
- 为候选连接器准备合规的测试租户、OAuth 授权和测试数据；不得通过聊天传递账号密码。
- 输出连接器能力与 POC 报告，以及 Windows/macOS 的测试矩阵。

## 文档同步提醒

当前代码已完成三步 Onboarding，但原 Onboarding PRD 仍存在“四步 + Trial”的历史描述。应以本会议结论统一 PRD、交互稿、测试用例和排期，避免开发依据不一致。
